01

What the old benchmark got wrong

The --benchmark command reported 44.3 ms per detection on the Windows machine and concluded about 1 camera. The 44.3 ms was probably accurate. The conclusion drawn from it was wrong three separate ways, and the errors did not cancel.

  1. It timed a stopwatch, not a bill. A detection that takes 44 ms of wall clock on four cores costs the machine up to 176 ms of CPU, spread thin. Dividing wall-clock latency by detect_fps quietly assumed the other three cores were free. They were being used by the same detection.
  2. It never looked at the video. Receiving and decoding one 1080p30 stream costs about 193 CPU-ms every second, per camera, before any detector runs. The analyzer pays that whether or not it looks at the frame. On a fast detector it is now the largest single line in the budget.
  3. It measured random noise at 720p. Random pixels produce almost no detections, so the NMS stage — a real per-frame cost — never ran, and the frame size did not match what the cameras actually send.

The practical damage: an owner with a perfectly serviceable machine was told to plan for one camera per store. The patched benchmark in the worktree prices a whole camera-second and divides by the whole machine.

Same box, both numbers

On the machine I measured on, the shipped benchmark logic reports 2.6 cameras and a real-time soak of the shipped code holds 2–3. So the arithmetic was not wildly optimistic — it was measuring the wrong thing, on hardware whose speed it then had no way to convert into a camera count.

The line nobody had priced

Colour conversion was being bought thirty times a second and used six

WebRtcFrameSource._pump called to_ndarray(format="bgr24") on every frame aiortc handed it — 30 a second — and the loop then discarded four out of five because detection is rate-limited to 6. At 3.04 CPU-ms a conversion that is 73 CPU-ms per second per camera bought and binned, about a fifth of a whole camera's budget, per camera. The fix is a lazy wrapper: hold the frame, convert past the rate limiter.

03

Testing the decode-ceiling hypothesis

The working hypothesis was that video decode is the real ceiling — roughly 16 cameras on a 4-core box. The number is close to right. The reason is not.

One core of the measured machine decodes a 1080p30 H.264 stream in 3.14 CPU-ms per frame, which is 10.6 streams per core, or about 42 concurrent 1080p30 streams on four cores if decoding were all you did. At 720p it is 1.47 ms per frame — 22.7 streams per core. Decode is not what stops you at 16, or anywhere near it.

What does sit next to decode in the budget is the thing above it in the stack. Holding a real WebRTC stream costs 6.44 CPU-ms per 1080p frame end to end; only 3.6 of that is the decoder. The other 2.8 ms is aiortc — RTP depacketization, SRTP decryption, the jitter buffer, the asyncio machinery — and it is Python. Verdict on the hypothesis

~16 cameras on a 4-core box is a good number arrived at for the wrong reason, and it is optimistic once WebRTC is included. Decode alone would allow 42. Inference, even after a 5× speed-up, is still 131 CPU-ms/s against decode's 94. The realistic figure is 9 cameras at 1080p30 and detect_fps 6 — and the constraint you hit is a three-way tie between aiortc, libavcodec and the network, not any one of them.

Hardware decode would help less than it sounds: it addresses at most the 94 ms decode line and none of the 84 ms aiortc line, and aiortc has no hook to use it — it drives PyAV's software decoder with no way to swap in QSV or VAAPI without patching the library. I could not test it here in any case: this VM has no /dev/dri.

Read that table sideways

Multi-threaded inference makes one camera faster and the machine smaller

Going from one thread to four cuts the latency of a detection but raises its cost by 2.15× on OpenVINO and 1.72× on PyTorch. The analyzer today runs one loop and lets PyTorch spread each detection over every core — the worst square on this table, at 175.8 CPU-ms, against 20.0 for the best. That single structural choice is a 8.8× difference in how many cameras a box holds, and it costs nothing to change: cameras are already parallel work, so give each one a core rather than giving each detection four.

The instruction set matters more than the core count

This is the finding that should drive the hardware decision. The measuring machine is an Emerald-Rapids-class Xeon with AVX-512 and AMX, and OpenVINO silently runs the graph in bfloat16 on it. Capping oneDNN at AVX2 — which is all an N100 or a Ryzen-mobile mini PC has — on the very same silicon, at the very same clock:

A 5× spread on identical silicon. OpenVINO's advantage over PyTorch collapses from 4.8× to 1.3× the moment AVX-512 is gone. Buying a cheap mini PC does not just buy slower cores; it buys cores that cannot run the fast path at all. On AVX2 hardware, ONNX Runtime is the better engine — though I could not verify that directly, because ONNX Runtime uses its own MLAS kernels and ignores the oneDNN switch I used to cap the instruction set, so its AVX2 row is unmeasured.

A trap that costs you the whole machine

OpenVINO pins its threads, and every process picks the same core

Running one analyzer process per camera with OpenVINO's default settings, eight workers took 159 ms of wall clock for 27 ms of CPU each while the machine sat 61% idle. OpenVINO pins inference threads to specific cores and chooses them per process, knowing nothing about its neighbours, so all eight pinned to core 0. ENABLE_CPU_PINNING: False fixes it completely. A box that looks bored and still cannot keep up is the hardest kind of capacity bug to find, and it is set in the patched detector.

Two things I want to be blunt about

ROI cropping to the doorway is slower, not faster, if you keep the input size. Cropping a 1080p frame to the entrance region and letterboxing that to 640 gives 640×448 — more pixels than the 640×384 the full frame produces, because the crop is squarer. Measured: 70.1 ms cropped against 59.0 ms uncropped. ROI only pays if you shrink the input in proportion, at which point it is really the resolution dial wearing a hat.

Motion gating is not a general win. The gate itself is nearly free (0.19 ms per frame at 160×90). On footage with people in it continuously, it saved nothing at all. On an empty shop it dropped detection from 126.9 to 3.4 CPU-ms/s — a 37× reduction. So its value is exactly the fraction of the day a camera sees no motion, which is a per-store fact I do not have. It is worth adding — it can only help — but do not size hardware on it.

Batching I did not measure, and I would not pursue it. Cameras arrive asynchronously, so batching means holding early frames until late ones show up — buying throughput with the one thing a door counter cannot spend, which is timing.

The capacity model, and where it breaks

The model is arithmetic on measured coefficients. A camera costs stream_fps × (rtp + decode) + detect_fps × (bgr + infer + post) + 65 CPU-ms per second; a machine has cores × 1000 × 0.93 to spend. The 0.93 is not a safety margin — it is the measured ceiling a real-time soak reached before cameras began to slip.

Five ways this model is wrong

  1. It is an average. Decode cost rises with motion and NMS with people in frame, so a shop at 5pm is dearer than the same shop at 3pm. The test footage holds four people continuously — busy, but not a worst case.
  2. It assumes the stream arrives at 30 fps. If Nest drops to 15 in low light, receive and decode halve and the box gets cheaper. Assuming 30 is the safe error; assuming 15 is not.
  3. It treats memory bandwidth as free. On four cores it never bound. On sixteen cores with sixteen cameras it might, and the model would not see it coming.
  4. It says nothing about Google's API limits, which bound a central deployment before CPU does. See below.
  5. The coefficients come from one CPU. The inference term moves 5× with instruction set alone. Re-measure on the machine you actually buy — --benchmark now does exactly this.
06

Deploying to 18 stores

Start here

Putting a box in the store buys you nothing

Nest cameras stream from Google's cloud, not over the shop LAN. A machine in the stockroom pulls the same bytes over the same public internet as a machine in a rack — it just does it from somewhere with a consumer ISP, no remote hands, and a cleaner who can unplug it. "Edge" here has all of the operational cost of edge and none of the locality benefit. And with one camera per store, an edge box runs at about 11% utilisation.

Not recommended

A box per store

18 × ~$170 = ~$3,100 one-off

Cheapest on paper. Eighteen failure points in retail stores, eighteen site visits when something needs a hand, eighteen machines at a tenth of their capacity. One store blind is the failure mode, which is the one genuine advantage — but you are paying for it eighteen times over.

Recommended

Two boxes, one per metro

~$1,100 one-off, or ~$105/mo hosted

Roughly 10–11 cameras each, which every option below carries comfortably. Halves the blast radius against a single box, and each can be sized to pick up the other's cameras at a reduced detect_fps if one dies. It also keeps you under Google's per-account command limits if the two metros sit on separate Google accounts.

Workable

One central machine

~$260–520/mo cloud

Simplest to operate and what the analyzer's own design notes argue for. The trade is stated plainly in that code: one box down is every store blind. At 21 cameras you also need 9–13 physical cores, which is a large enough VM that two smaller ones cost the same.

Bandwidth, and what I do not know about it

Sustained ingress for a central deployment is cameras × bitrate, plus about 5% for RTP and UDP headers. I do not know Nest's actual bitrate and will not guess it; the figures below use the 2 Mbps my 1080p test clips were encoded at, which is a plausible midpoint and nothing more.

On AWS and GCP ingress is free, so this is a capacity question, not a billing one. On a budget host or an office broadband line it is neither: several providers cap total traffic in the 1–8 TB range, which the middle row alone would exceed. Check the traffic policy before choosing a host, and check whether it counts inbound.

Unverified, and important enough to verify

Google's command rate limit may bind before your CPU does

Google documents devices.executeCommand at 5 queries per minute per project, per user, per device, and secondary sources report an aggregate ceiling of 10 QPM for a project's user across all devices. I could not read Google's limits page directly — this network blocks developers.google.com — so treat the aggregate figure as unconfirmed.

If it is right, it matters a great deal. Holding a WebRTC stream open means calling ExtendWebRtcStream roughly every 200 seconds, so 21 cameras generate about 6.3 QPM sustained — inside 10, but with very little room. Worse, the analyzer as written opens every camera in one pass of its loop, so a cold start fires 21 commands in about a second, gets throttled, retries, and gets throttled harder. Every camera then looks offline for reasons that have nothing to do with cameras.

I have added a token-bucket budget (--open-qpm, default 4) that spaces stream opens and lets extensions win, since a missed extension costs a full renegotiation. Verify the real quota in the Google Cloud console under smartdevicemanagement.googleapis.com before committing to a single-account central deployment — and note that splitting the two metros across two Google accounts doubles the ceiling for free.

What to actually buy

Named machines, with the reasoning attached. Prices are what I could find in August 2026 and should be treated as indicative — check them. Every one of these should be run through --benchmark before purchase; that is what the command is for.

Best value

2 × AMD Zen 4 mini PC

~$500–600 each · ~$1,100 total, one-off

A Ryzen 7 8845HS or 7840HS box — Minisforum UM890, Beelink SER8 and similar — 8 cores, 32 GB. Zen 4 has AVX-512, which puts it in the fp32 row at roughly 13 cameras per box: two cover 21 with real headroom. Caveat I must flag: I measured AVX-512 on Intel silicon, and OpenVINO's AVX-512 path on AMD is unmeasured. Benchmark one before buying two.

No hardware to own

2 × Hetzner CCX33

~$52/mo each · ~$105/mo

8 dedicated AMD EPYC vCPUs and 32 GB each. Same AVX-512 fp32 profile, same caveat about AMD being unmeasured, and vCPUs are threads rather than cores so derate accordingly. Cheapest hosted option by a wide margin — but US plans carry 1–8 TB traffic allowances, so confirm inbound is free before you commit.

Fastest per core

AWS c7i.4xlarge

~$0.71/hr · ~$520/mo on demand

16 vCPU = 8 physical Sapphire Rapids cores with AMX — the only option here that runs the 17.1 ms bf16 path I measured, at about 19 cameras. Free ingress and no hardware to own. Five times the running cost of the mini PCs; a one-year reservation takes roughly a third off, and stopping it overnight takes more.

Only if per-store

Intel N100 mini PC

~$150–180 each

AVX2 only, so it lives in the slowest row — modelled at 4.6 cameras, and that is generous because my AVX2 figure came from a capped server core rather than an N100. Ample for the one or two cameras a single store has. Do not build the central plan on these.

Worth a test I could not run

A Core Ultra mini PC (the GMKtec K9 with a Core Ultra 5 125H was around $361) has an NPU that OpenVINO can target with device_name="NPU". That could be a substantial win on cheap hardware and would change the recommendation — but there is no NPU in this environment and I will not estimate it. One machine, one afternoon, one --benchmark run settles it.

One thing I am handing to the accuracy work

The fast detector does not produce bit-identical counts, and I did not chase it, because counting accuracy is not my ground.

On boxes it is very close: 75 of 76 person boxes matched the PyTorch answer at IoU above 0.976, with the one disagreement sitting at the confidence threshold. But replaying the same clip through the real CameraWorker, PyTorch produced 10 line crossings, OpenVINO in bf16 produced 11, and OpenVINO in fp32 produced 10 in a different in/out order. A box that moves by a pixel at the threshold becomes a different track under the IoU tracker, and a different track can be an extra crossing.

That was a stress case — a synthetic clip with four people looping across a mid-frame line, detecting every frame rather than six times a second — so I would not read a failure into it. But it is a real signal about how sensitive the tracker is to marginal boxes, and it needs a verdict on real footage before bf16 ships. --ov-precision f32 gives up half the speed-up and stays numerically much closer; --no-openvino restores the original path exactly. Both are there so the choice can be made on evidence rather than by default.

Measured on a 4-core Intel Xeon (Emerald Rapids class, 2.10 GHz, AVX-512 + AMX, 15 GB RAM), Python 3.11, OpenVINO 2026.3, ONNX Runtime 1.29, PyTorch 2.13, aiortc 1.15, PyAV 17.1. Some runs shared the machine with another agent's workload; every per-detection and per-frame figure is CPU-time rather than wall-clock and is unaffected, and the real-time soaks were run on an otherwise idle box.
